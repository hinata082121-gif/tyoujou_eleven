## 1. 横画面への変更

### 1.1 向きの固定と、縦に持ったときの画面

- 全画面を横画面向けに作り直す。今の「幅 430px の縦長の箱」（`src/app/layout.tsx`）はやめ、画面いっぱいを使う。
- **縦に持ったとき**：CSS の `@media (orientation: portrait)` で、ゲーム画面の代わりに「端末を横向きにしてください」の画面（回転を示す SVG の絵と一文）を出す。ゲームの状態は止めるだけで消さない（試合の観戦中も、時計を止める）。
  - スマホ・タブレット・PC の区別はせず、**縦長の画面ならどれでも**この画面にする（PC で縦長のウィンドウにした場合も同じ）。11章 Q3。
- **アプリとしてホーム画面に追加したとき**：Web アプリのマニフェスト（`src/app/manifest.ts`。静的書き出しで `manifest.webmanifest` になる）に `"orientation": "landscape"`・`"display": "fullscreen"` を入れる。アイコン（192px・512px）もゲーム用に描いて入れる。
  - 補足：iPhone の Safari はマニフェストの向きの設定を無視するので、縦に持ったときの画面が引き続き必要。Android でホーム画面から開いたときは横向きで固定される。将来のアプリ化（Capacitor など）では、アプリの設定で横向きに固定する。

### 1.2 画面の大きさと、伸び縮みの方式

想定する大きさ（依頼書 1章）：

| 区分 | 大きさ（CSS の px） | 縦横比 |
|---|---|---|
| スマホ横（小） | 667×375 | 1.78 |
| スマホ横 | 844×390 | 2.16 |
| スマホ横（大） | 932×430 | 2.17 |
| タブレット横 | 1024×768 | 1.33 |
| PC | 1280×720 〜 1920×1080 | 1.78 |

- **基準は高さ 375〜430px のスマホ横向き**。いちばん狭いのは高さなので、画面は「縦に詰め込まず、左右に並べる」作りにする（左に一覧・操作、右に詳しい情報、のように）。
- **大きさの合わせ方（11章 Q2）**：文字と部品の大きさは**画面の高さで段階的に**変える（高さ 360〜539px：1 倍、540〜799px：1.25 倍、800px 以上：1.5 倍。CSS の `rem` の基準を変えるだけ）。横幅の余りは、各画面の「主な列」（ホームならカレンダーと手札）に回す。
  - タブレット（1024×768）は 1.25 倍になり、縦の余りで一覧の行が多く見える。
  - PC の 1920×1080 は 1.5 倍で、スマホとほぼ同じ見た目のまま大きく表示する。縦横比が 2.4 より横長（ウルトラワイド）なら、中央に寄せて左右は背景にする。
- 1 画面にどうしても入らないもの（部員の一覧・トーナメント表など）は、その枠の中だけを縦か横にスクロールさせる。画面全体はスクロールさせない（ゲームらしく、枠の位置が動かないようにする）。

### 1.3 ノッチ・ホームバー（セーフエリア）

- `viewport` に `viewport-fit=cover` を入れ、`env(safe-area-inset-*)` を CSS の変数（`--safe-l` など）に入れて使う。
- **背景（芝・紙などの質感）は画面の端まで**塗り、**文字・ボタン・操作の部品はセーフエリアの内側**にだけ置く。iPhone の横向きでは左右 47px 前後・下 21px 前後が空く。
- 試作のスクリーンショットは、このセーフエリア（左右 47px・下 21px）を空けた状態で撮っている。

### 1.4 確認の方法（依頼書の「計画で確認方法を提案」）

1. **自動のスクリーンショット**（Playwright・Chromium。作業用のスクリプトで撮る。リポジトリには入れない）
   - 上の表の 6 つの大きさ（667×375・844×390・932×430・1024×768・1280×720・1920×1080）と、縦向き（390×844）で全画面を撮る。
   - **セーフエリアの再現**：ブラウザでは切り欠きを再現できないので、開発用に `?safe=notch` を付けると、セーフエリアの変数に iPhone の値（左右 47px・下 21px）を入れる仕組みを作る（`?perf=1` と同じく、通常の画面からは見えない）。スマホ横の 3 つの大きさは、この状態でも撮る。
   - 撮ったあと、**はみ出しの自動検査**をする：各画面で、文字やボタンの要素が親の枠や画面の外にはみ出していないか、セーフエリアに重なっていないかを、要素の位置を調べて一覧にする（目で見るだけだと見落とすため）。
2. **実機での確認**（ひさんにお願いしたいこと）：Vercel のプレビューの URL を、お手元のスマホで横向き・縦向きに開いていただく。ホーム画面に追加したときに横向きで開くかも見ていただく（Android のみ）。

## 2. UI デザインの全面刷新

### 2.1 今の問題と直し方

| 今の問題 | 直し方 |
|---|---|
| 角の丸い要素が多い（`rounded-xl` など） | 角は直角が基本。使っても 2px まで。Tailwind の角丸の値を基本値で上書きし、`rounded-xl` などを使えなくする（lint で検出する） |
| 標準的なゴシック体だけ | 見出し用・本文用（・数字用）のフォントを案ごとに選び、自分のサイトから配信する（2.4） |
| 無難な色 | 案ごとの独自の配色を基本値にする。Tailwind の標準の色（`bg-gray-*`・`text-sky-*` など）は使わない（lint で検出する） |
| 絵文字 | すべてなくし、ゲーム用に描いた SVG のアイコンにする（2.5・2.7） |
| どの画面も同じ形のカード | 画面の役割ごとに見せ方を変える：操作の画面（すごろく・試合前）、情報の画面（部員・記録）、場面（イベント・卒業式・試合結果）、観戦の画面。見出しの帯・枠・区切り線・背景の質感を、それぞれに合ったものにする |

### 2.2 方向性の試作（3 案）

依頼書の 3 つの方向性で試作した。横画面のホーム（すごろく）と選手の詳細に加え、3章のキャラクター表示が分かるように**イベントの場面**も作った。キャラクターは Phase 4a の見た目の生成と絵（`src/components/look/Figure.tsx`）をそのまま使っている（スタッフの服だけ試作で足した）。データは実際のゲームの状態（新しく始めた学校で数枚カードを使ったところ）から取った。

| 案 | 雰囲気 | フォント | 配色の中心 | 試作 |
|---|---|---|---|---|
| **A 部室・ノート風** | 方眼ノート・黒板・付箋・マスキングテープ・赤ペンの丸。監督の手帳をめくる感覚 | 見出し：Yusei Magic（マーカーの手書き風）／本文：BIZ UDPGothic | 紙 #f2ede0・インク #24313b・黒板 #2e4a3d・赤ペン #c43e2c・マーカー #f0cf4a | `A_note_*.png` |
| **B スポーツ中継風** | 芝の刈り目の背景に、斜めに切った帯・スコアボード風の上の帯・速報のテロップ。数字は細長い英数字で力強く | 見出し：Dela Gothic One／本文：M PLUS 1／数字：Oswald | 芝 #1d3b2b・墨 #0f1714・テロップ #f3f0e6・黄 #f2c21b・赤 #d6372b | `B_broadcast_*.png` |
| **C レトロゲーム風** | ドットの文字、二重線のウィンドウ、市松模様の芝、ドット絵のアイコン、コマンドを選ぶ矢印 | 見出し・操作：DotGothic16／小さい文字：BIZ UDPGothic | 窓 #1f2552・枠 #f3eedb・琥珀 #f2b134・芝 #3f8f45 | `C_retro_*.png` |

どの案も 2.1 の基本ルール（角丸なし、独自のフォントと配色、絵文字なし）を守っている。

**おすすめは B（スポーツ中継風）**（11章 Q1）。理由：

- 試合まわりの画面（スコアボード・速報・スタメン発表・試合結果）と相性がよく、3D 観戦の上に重ねる表示（スコア・速報）とホームの見た目が一続きになる。全国の頂点を目指すゲームの「大舞台」の感じも出しやすい。
- 黄・赤の帯で「大事な情報」（試合の日・能力の上昇・評判の変化）を強く見せやすい（2.6）。
- 気になる点：暗い背景なので、明るい屋外ではやや見にくい。本文の文字は明るい色・十分な大きさにし、試作より少しコントラストを上げる。
- A は温かみがあり育成の画面に合うが、試合の画面では「手帳」との行き来が不自然になりやすい。C は懐かしさが強い一方、ドットの文字は小さい文字（12px 未満）で読みにくく、試合の画面の情報量を入れにくい。
- 案を混ぜる（たとえば B を基本に、作戦ノートの画面だけ手帳の質感にする）こともできるが、全体の統一を優先して、混ぜない形をおすすめする。

### 2.3 デザインの基本値（`docs/DESIGN.md` に書くもの）

選んだ案で、次を CSS の変数（`src/app/globals.css` の `:root`）と Tailwind のテーマ（`@theme`）にまとめ、`docs/DESIGN.md` に表で書く。今後のフェーズの画面もすべてこれに従う。

- **色**：背景（2〜3 段）、文字（主・副・淡）、強調（2 色）、良い・悪い・注意、すごろくのマスの 8 種、ランク（G〜SS）の 9 色、体力のバーの 3 段。
- **フォント**：見出し・本文・数字の 3 種類と、文字の大きさの段（10・12・14・16・20・28・40px 相当）。本文は 12px 未満にしない（例外は、すごろくのマスの中の短いラベルだけで、ここは 10px まで）。
- **余白**：4px 単位（4・8・12・16・24）。
- **枠の線・角**：線の太さ 1・2・3px、角丸は 0（使っても 2px まで）。
- **影**：ずらした影（ぼかさない）を 2 段。
- **部品の形**：見出しの帯、ウィンドウの枠、表の行、ボタン（主・副・危険・小）、タブ、スイッチ、ランクの札、バー、チップ（特殊能力）、ダイアログ、せりふの枠、トースト（短い知らせ）。
- **動き**：押したとき（2.6）、画面の切り替え、大事な情報の演出の長さとイージング。
- **してはいけないこと**：角丸、標準の色、紫系のグラデーション、絵文字、ぼかした大きな影、どの画面も同じ形のカードを並べること。

### 2.4 フォントの配信

- `next/font/google` で読み込む。ビルドのときに Google Fonts からファイルを取ってきて、**自分のサイト（`out/_next/static/media/`）から配信する**。静的書き出しで動き、アプリにしたときも同じファイルを中に入れればオフラインで表示できる。
- 日本語のフォントは文字の範囲ごとに細かく分けたファイルになり、ブラウザは画面で使う文字の分だけを読む。B 案なら初めの表示で読むのは数百 KB 程度の見込み（ビルドの出力の合計は数 MB 増える）。実際の大きさは実装後に測って報告する。
- 使う太さは最小限にする（B 案：Dela Gothic One 400、M PLUS 1 の 400・700・900、Oswald の 500・700）。

### 2.5 アイコン

- ゲーム用の SVG のアイコンを `src/components/icons/` に描く（24×24 の線と面。選んだ案の線の太さ・角の形に合わせる。C 案ならドット絵）。
- 必要なもの：練習 11 種、下のメニュー 5 種（すごろく・部員・大会・記録・メニュー）、ケガ・出場停止・カード（黄・赤）・ゴール・交代・調子 5 段・矢印（戻る・進む・上・下）・閉じる・設定・保存・ユニフォーム・設備・スカウト・作戦ノート・キャプテン・速さ（1・2・4 倍）・一時停止・再生・削除・並べ替え・回転（縦持ちの画面）など、およそ 50 個。
- 試作のアイコン（練習・メニュー）は、方向性を見るための仮のもの。

### 2.6 押したときの反応と、大事な情報の演出

- **押したとき**：ボタンは押している間 2px 沈み（影が縮む）、色が一段暗くなる。離すと 120ms で戻る。手札のカードは押すと少し沈み、使うと場から抜ける動き（200ms）。
- **大事な情報**には短い演出を付ける（タップで飛ばせる。合計 1 秒前後まで）。
  - 試合の日（すごろくで大会のマスに止まった）：斜めの帯が横切って「県予選 1 回戦」などを出す。
  - 能力の上昇：上がった数字が一瞬大きくなり、＋の数が帯で出る。特殊能力の習得は札が飛び込む。
  - 評判の変化：評判のゲージが伸び、段が上がったときは名前が切り替わる演出。
  - 試合結果：スコアが帯で入り、勝ったときと負けたときで色と動きを変える。
- 演出の長さは基本値（2.3）にまとめ、「移動の演出をスキップ」の設定がオンのときは短くする。端末の「視差効果を減らす」設定（`prefers-reduced-motion`）のときも短くする。

### 2.7 絵文字の撤去

- 今、絵文字があるのは、画面の部品（`HomeView`・`PlayScreen`・`MatchScreen`・`MenuView`・`FlowScreens`・`Phase2cScreens`・`NotesScreen`・`BracketView`・`TitleScreen`・`UniformEditor`・`SquadView`・`PkScreen`）と、**エンジンの試合の文章**（`src/engine/match/text.ts` の 🟨・🟥・✚）。
- エンジンの文章の絵文字も消し、速報の行の頭に、イベントの種類（カード・ケガ）からアイコンを付ける形にする。文章を変えるだけで乱数は使わないので、試合の結果は変わらない（11章 Q4）。
- **◎・○・△・×**（ポジション適性・特殊能力の段階）は絵文字ではなく記号なので、文字のまま残す（11章 Q4）。調子の矢印（↗ など）・戻るの ← などの記号は、アイコンに置き換える。
- 最後に、ソースコードを絵文字の文字の範囲（`U+1F000〜1FAFF`・`U+2600〜27BF`・異体字セレクタなど）で検索し、残っていないことを確かめる。テストにも入れて、今後混ざらないようにする。

## 3. 選手・スタッフのキャラクター表示

### 3.1 共通の絵

- 顔と全身の絵は、Phase 4a の `src/components/look/Figure.tsx`（3D と同じ見た目の生成から描く SVG）を使う。同じ選手は 2D の絵でも 3D でも同じ見た目になる。
- 体型（身長・フィジカル）と背番号・ユニフォームも 4a と同じ。

### 3.2 スタッフの見た目（11章 Q7）

- **OB のスタッフ**：OB の見た目（在学中のもの。`Alumnus.look`）を引き継ぐ。
- **臨時コーチ**（OB でない）：スタッフの ID とゲームのシードから、4a と同じ別の系統の乱数で生成する（ゲームの乱数は使わない）。
- **年齢による変化**（表示のときに計算する。保存しない）：
  - 35 歳から髪の色を少しずつ灰色に寄せ、55 歳以上はかなり白髪まじりにする。
  - 45 歳以上は体の厚みを少し足す（最大 1.08 倍）。
  - 髪型は変えない（その人だと分かるように）。
- **服装**：選手のユニフォームとはっきり区別できる形にする。
  - ヘッドコーチ・分析担当：学校の色のポロシャツと長ズボン（分析担当はバインダーを持つ）。
  - フィジカルコーチ：学校の色のジャージの上下。
  - GK コーチ：GK 用の色のジャージの上下。
  - 色は学校の 1st のメインとサブから決める。
- 試作のイベントの場面で、ポロシャツと長ズボンの形を見ていただける（`*_event.png`）。
- **セーブデータは変えない**（スタッフの見た目は、OB の見た目と ID から毎回同じものを作る）。

### 3.3 表情

- 4a の表情（普段・集中・笑顔・悲しい）に、**驚き**と**悔しい**（歯を食いしばり、眉を寄せる）を足す。2D の SVG に足し、3D の顔の絵（`src/view3d/textures.ts`）にも同じものを足す（3D で使うのは 4b）。
- イベントの場面では、出来事の良し悪し（`tone`）と種類から表情を選ぶ（良い：笑顔、悪い：悔しい・悲しい、ケガ：驚き → 悲しい、OB・スタッフの指導：笑顔と集中、など）。表情の選び方は表にして `src/components/` に置く（エンジンには置かない）。

### 3.5 イベントの場面（11章 Q5・Q6）

- 今は、カードを使ったあとに出来事の文章をホームの枠に並べている。これを、**出来事 1 つずつの場面**にする：背景（グラウンド・部室など、出来事の種類で選ぶ）に関わる人の立ち絵を並べ、下にせりふの枠（話している人の名前・学年や役割）を出す。タップで次へ進む。結果（特殊能力の習得・能力の上昇・ケガ）は、場面の上に札で強く見せる。
- **文章**：今のイベントの文章をそのまま、せりふの枠で見せる。名前の札は、出来事の中心の人（OB・スタッフ・選手）にする。今の文章は「〜が〜した。」という語りの形が多いので、R1 では語りの形のまま見せ、**話し言葉への書き直しは R2**（選択肢のあるイベントを作るとき）に回す（11章 Q5）。試作の場面のせりふは、R2 で書き直したときの見え方の例。
- **誰が出てくるか**：今のエンジンの出来事の結果（`EventOutcome`）には、関わった選手の名前（`targets`）はあるが、OB やスタッフが誰かは文章の中にしかない。そこで、**エンジンの出来事の結果に、表示用の項目（関わった人の種類と ID）を足す**ことを提案する（11章 Q6）。乱数は使わず、値を書き足すだけなので、ゲームの結果は変わらない（`balance:quick` が同じであることで確かめる）。名前から人を探すと、同じ名前の人がいたときに間違えるため。
- **設定**：「イベントの場面」を「場面で見る（標準）／文章だけ」から選べるようにする。文章だけのときは、今のようにホームに並べる（アイコン付き）。

## 10. 気になる点

- **暗い背景（B 案）と屋外**：本文の文字のコントラストを高めにし（WCAG の 4.5:1 以上を基本値で確かめる）、細い文字は使わない。
- **フォントのファイルの大きさ**：日本語のフォントは合計で数 MB になる。初めの表示で読むのは使う文字の分だけだが、アプリにするときは中に入れる大きさが増える。足りない文字だけを抜き出す処理は、アプリ化のとき（Phase 5）に考える。
- **3D 観戦のコードの読み込み**：4a の報告のとおり、トップの画面の JavaScript が 4a で 14KB 増えている（3D ではなく UI の部分）。R1 で画面を作り直すときに、観戦の画面のコードは開いたときだけ読む形に分ける。
