# Phase 1 実装依頼

あなたはこのリポジトリの実装担当です。高校サッカー部の監督として学校を育てるブラウザゲームの、**Phase 1（1年が回る最小限のゲーム）**を作ってください。

## 0. 最初にやること

1. `CLAUDE.md` と `docs/SPEC.md` を全部読んでください。仕様の正本は `docs/SPEC.md` です。
2. **いきなりコードを書かず、まず実装計画を出してください。** 計画には次の内容を含めてください。
   - ディレクトリ構成
   - 主要な型（School、Player、Match、Calendar、SaveData など）の設計
   - 試合エンジンの判定式の初期案
   - 作業の順番
3. 私が計画を承認してから実装を始めてください。仕様があいまいな点や、仕様にない判断が必要な点は、計画の段階でまとめて質問してください。

## 1. 技術要件

- Next.js（App Router）＋TypeScript（strictモード）。`output: 'export'` による静的書き出しのみで動かし、Vercelにデプロイします。サーバー機能は使いません。
- 状態管理はZustand、テストはVitestを使います。スタイルはTailwind CSSで構いません。
- `src/engine/` はReactやDOMに依存しない純粋なTypeScriptにします。
- 乱数はシード付きの疑似乱数（PRNG）を使い、その状態をセーブデータに含めます。
- バランス調整用の数値は `src/engine/config/` に、表示名は `src/engine/config/names.ts` に集約します。
- UIはスマホ縦画面を最優先にします（幅360〜430px）。PCでは中央に縦長で表示します。
- `docs/SPEC.md` 3章の知財ルールを厳守します。学校名・地名・大会名は架空のもの、または仮の名前にします。

## 2. Phase 1 で作るもの

### 2.1 ゲームの開始
- タイトル画面と、セーブ枠3つの選択画面。
- 学校の作成
  - 学校名を入力する。
  - 架空の県（16〜32校）と全国の学校群を自動で生成する。
  - 初期の部員を生成する。1〜3年生がそろった状態で、評判は「弱小」から始める。
  - CPUの学校にもランク（E〜S）と部員を生成する。

### 2.2 すごろく式のカレンダー（SPEC 5章）
- 4月始まりで1年分のカレンダーを作る。手札の枚数は評判で決まり、数字1〜5の進行カードを使う。
- マスは、青・赤・白・緑・黄・大マス（必ず止まる）の6種類。
- 経験点は「練習1日あたりの値 × 進んだ日数」。必ず止まるマスの手前では、止まった日数分しか効果がない。
- 練習カードは、SPEC 5章の表のうち「PK練習」以外のすべて。
- イベントは10〜15種類（体力回復、ケガ、やる気アップなど）。
- 体力・調子・ケガの仕組みは簡易版でよい。

### 2.3 選手（SPEC 7章）
- 能力項目とランク（SS〜G）は、SPEC 7.1・7.2の通りにする。身長はcmで表示する。
- ポジション適性（◎/○/△）と利き足を持たせる。
- 成長：能力値が高いほど上がりにくい仕組みと、隠しパラメーター「伸びしろ」による補正を入れる。
- 部員一覧画面（並べ替え、ポジションで絞り込み）と、選手の詳細画面を作る。

### 2.4 新入生・引退・卒業（SPEC 4・6・8章）
- 4月に、評判で決まる1学年の人数分の新入生を生成する（Phase 1では特待生スカウトがないので、全員一般入部）。
- 3年生は、冬の選手権で敗退した時点で引退する（優勝した場合は全国大会の終了後）。3月に卒業し、進路付きのOBとして記録する（スタッフ制度はPhase 2で使う）。

### 2.5 試合エンジン（SPEC 10章）
- SPEC 10.1の原則を守る。確率でイベントを生成し、5分ごとの区間で計算を進め、采配の変更は次の区間から反映する。
- SPEC 10.3の判定モデルと、7.3の能力の組み合わせを再現する。特に次の3つ。
  - 視野の広さ×判断（見えていても、強い相手には出せない）
  - キック力とパス・シュートの組み合わせ
  - GKのポジショニング→セービング→キャッチング（こぼれ球）の流れ
- フォーメーション5種類と戦術4項目（SPEC 10.4）。
- 疲労とスタミナ。
- 大会ごとの試合ルール（試合時間、延長の有無、交代5人、交代回数制限のフラグ）はデータとして持つ。
- PK戦：プレイヤーが決められるのはキッカーの順番だけ。判定はSPEC 10.6に従い、スカウティングの項は0とする。試合中のPKも同じ判定を使う。
- CPU同士の試合も同じエンジンで計算する（表示はしない）。

### 2.6 試合の画面（テキスト版）
- 試合前の画面：スタメン11人、控え9人、フォーメーション、戦術を決める。
- 観戦画面
  - テキスト速報、スコアボード、試合の流れ（モメンタム）を表示する。
  - 等速（試合時間15分＝現実の1分）、2倍速、4倍速を切り替えられる。
  - いつでも一時停止して、交代や戦術変更ができる。
- ハーフタイムの画面：交代、フォーメーション変更、戦術変更ができる。
- PK戦の画面：キッカーの順番を決め、1本ずつの結果を演出して表示する。
- 冬の選手権は「観戦のみ」とし、結果だけを表示するモードは使えないようにする。
- 練習試合は、Phase 1では観戦ありのみでよい。

### 2.7 大会と評判（SPEC 6・11章）
- 冬の選手権：県予選トーナメント → 全国大会トーナメント（32校）。トーナメント表の画面を作る。
- 練習試合のマス。
- 評判は5段階で、ゲージ制にする。上がり方・下がり方はSPEC 6章に従う。評判が変わったら、手札の枚数と次の年度の新入生数に反映する。

### 2.8 セーブ（SPEC 12章）
- localStorageのセーブ枠3つ。日付が進むたび、試合が終わるたびにオートセーブする。
- セーブデータにスキーマのバージョンを持たせ、マイグレーションの仕組みを用意する。
- JSONでセーブデータを書き出し・読み込みできるようにする。

## 3. Phase 1 では作らないもの（拡張しやすい作りにはしておく）

- 作戦ノート

- 特待生スカウト
- 性格
- 特殊能力
- 分岐マス
- 夏の全国大会、新人戦、合宿
- リーグ戦と「結果のみ」モード
- 2D・3D表示
- アクセス解析
- 広告・課金

## 4. テストとバランス

- エンジンの単体テスト：乱数（同じシードで同じ結果になること）、カレンダー進行、経験点の計算、成長、試合の判定、PK、セーブのマイグレーション。
- `npm run balance` を用意し、大量の試合をシミュレーションして、SPEC 14章の目標値（平均得点、PK戦になる割合、同格の相手と格上の相手への勝率）を表形式で出力する。目標から外れていたら、`config` の数値を調整する。
- 「試合が少し強いチームに有利なだけで、運でひっくり返ることもある」という手触りを、実際に数値で確認してください。

## 5. 完了の条件

- 学校を作ってから、すごろくで1年を進め、冬の選手権を戦い（敗退するか優勝する）、3年生が引退し、卒業式を経て、翌年度の4月に新入生が入る。この流れが途切れずに2年以上続けて遊べること。
- リロードしても、セーブから再開できること。
- `npm run lint`、`npm run test`、`npm run build`（静的書き出し）がすべて通ること。
- スマホ幅（375px）で、すべての画面が操作できること。
- `CLAUDE.md` のコマンド欄を、実際のコマンドで更新すること。
